Vamos acelerar o desenvolvimento refinando uma tela central do app: Requisição de Materiais.

Tela foco:

* client/src/pages/requests.tsx
* client/src/pages/request-details.tsx
* client/src/components/request-dialog.tsx
* client/src/components/add-item-dialog.tsx
* client/src/components/duplicate-request-dialog.tsx

Objetivo:
Transformar a experiência de Requisição de Materiais em uma tela 10/10, com foco em design, layout, UX operacional, clareza do fluxo e segurança visual/funcional.

Contexto funcional:
A Requisição de Materiais permite que o usuário crie uma requisição em rascunho, adicione produtos/kits, envie para aprovação e acompanhe aprovação/rejeição. Requisições aprovadas alimentam Loading Orders e Estoque.

Direção visual:
Usar o Design System atual do EventFlow como fonte única de verdade.

Não criar novo Design System.
Não alterar tokens globais sem necessidade.
Não inventar padrões paralelos.

Aplicar:

* PageHeader
* PageSection
* FilterBar
* EmptyState
* PageLoading
* ErrorState
* StatusBadge
* DataCard
* ActionBar
* PermissionHint, se fizer sentido

Parte 1 — Lista de Requisições

Refinar client/src/pages/requests.tsx.

Melhorar:

1. Layout geral

* PageHeader com título “Requisição de Materiais”, descrição curta e botão “Nova Requisição”.
* Espaçamento consistente entre header, filtros e lista.
* Evitar conteúdo colado nas bordas.
* Garantir boa leitura em desktop, tablet e mobile.

2. Filtros

* FilterBar visualmente útil, não apenas uma linha vazia.
* Filtros mínimos:

  * Status
  * Evento
  * Área, se já existir no dado
* Usar badgeCount para filtros ativos.
* Usar onClear para limpar filtros.
* Campos em grid responsivo.
* Labels com text-xs text-muted-foreground.
* Botões alinhados.

3. Cards de requisição
   Aplicar padrão oficial do Design System:

* Card com hover-elevate border-border/60
* CardContent com p-4
* Header com StatusBadge + código/data + título + ação
* StatusBadge obrigatório
* Área como título principal
* Evento como contexto secundário destacado
* Código/ID ou data com text-xs text-muted-foreground font-mono
* Metadados separados com mt-3 pt-3 border-t border-border/40
* Grid de metadados com grid-cols-2 sm:grid-cols-4 gap-x-4 gap-y-1
* Botões dentro do card com size="sm"
* Card clicável ou botão “Detalhes” bem claro

Cada card precisa responder rapidamente:

* qual é a área?
* qual é o evento?
* qual é o status?
* quem solicitou?
* quando foi criada/enviada/aprovada?
* qual ação está disponível?

4. Estados vazios
   Criar EmptyState diferente para:

* nenhuma requisição criada;
* filtros sem resultado.

Se não houver requisições:

* mostrar ícone apropriado;
* texto claro;
* botão “Nova Requisição”.

Se filtros não retornarem nada:

* mostrar mensagem “Nenhuma requisição encontrada com os filtros atuais”;

Parte 4 — Segurança e RBAC

Verificar um ponto importante:

No fluxo atual, a lista aparentemente recebe todas as requisições do backend e filtra no front-end por requestedBy.

Valide no código se isso realmente acontece.

Se o backend retorna todas as requisições para usuário comum, isso deve ser registrado como risco de segurança, porque o front-end não deve ser a fonte da verdade de autorização.

Se possível corrigir com segurança e sem quebrar fluxo:

* usuário comum deve receber apenas próprias requisições;
* admin/supervisor devem receber requisições conforme permissão;
* o front pode manter filtro apenas como UX complementar.

Se essa correção exigir mudança maior de RBAC/back-end, não implemente agora sem isolar. Apenas registre como P0/P1 para correção.

Importante:
Não alterar fluxo funcional sem necessidade.
Não quebrar aprovação, duplicação, exclusão, envio ou adição de itens.
