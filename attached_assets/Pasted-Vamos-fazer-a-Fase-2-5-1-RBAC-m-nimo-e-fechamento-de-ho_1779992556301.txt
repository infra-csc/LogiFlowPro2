Vamos fazer a Fase 2.5.1 — RBAC mínimo e fechamento de holes críticos em Ordens de Carregamento.

Objetivo:
Fechar as rotas críticas abertas de loading-orders e aplicar RBAC mínimo em criação/edição/operação básica, sem criar roles novas e sem alterar regras de negócio, payloads ou banco.

Contexto:
A auditoria da Fase 2.5 identificou:

1. Rotas já seguras:

* GETs de loading-orders usam requireAuth.
* POST/DELETE /api/loading-orders/:id/trips já usam requireAnyRole([ADMIN, LOGISTICA]) desde a Fase 2.3.
* PATCH /api/loading-orders/:id já tem canEditResource, mas ainda usa auth inline e não tem role gate.

2. Riscos encontrados:

* POST /api/loading-orders/:id/approve não tem middleware.
* POST /api/loading-orders/:id/disapprove não tem middleware.
* POST /api/loading-orders/:id/mark-ready não tem middleware.
* POST /api/loading-orders usa req.isAuthenticated() inline, sem role gate.
* PATCH /api/loading-orders/:id usa req.isAuthenticated() inline + ownership, sem role gate.
* POST /api/loading-orders/:id/items usa apenas requireAuth, sem role gate e sem checagem suficiente de status.
* POST /api/loading-orders/:id/optimize usa check inline !req.user e mensagem fora do padrão pt-BR.

Decisões aprovadas:

1. Não criar role Almoxarifado agora. Fica para Fase 2.6.
2. Não criar role Supervisor/Aprovador agora. Fica para Fase 2.6.
3. Até existir Supervisor, approve/disapprove de loading-order será admin-only provisório.
4. Marcar como pronta será permitido para Admin ou Logística.
5. Criar/editar loading-order será permitido para Admin ou Logística, preservando ownership onde já existe.
6. Adicionar item avulso será permitido para Admin ou Logística provisoriamente, até existir Almoxarifado.
7. Executar otimização será permitido para Admin ou Logística.
8. Usuário comum continua podendo visualizar loading-orders via GET.
9. GETs não serão restringidos nesta fase.
10. Não consumir permissions/role_permissions no runtime.

Escopo permitido:

1. Back-end — aplicar RBAC nas rotas de loading-orders

Aplicar requireAnyRole([ROLES.ADMIN, ROLES.LOGISTICA]) em:

* POST /api/loading-orders
* PATCH /api/loading-orders/:id
* POST /api/loading-orders/:id/items
* POST /api/loading-orders/:id/mark-ready

Aplicar requireAdmin em:

* POST /api/loading-orders/:id/approve
* POST /api/loading-orders/:id/disapprove

Aplicar requireAnyRole([ROLES.ADMIN, ROLES.LOGISTICA]) em routes-optimization.ts:

* POST /api/loading-orders/:id/optimize

2. Preservar ownership e regras existentes

Para PATCH /api/loading-orders/:id:

* manter canEditResource após o role gate.
* admin continua tendo override.
* logística só edita se for owner, como já funciona hoje pelo canEditResource.
* manter bloqueios atuais por status/movimentos ativos.

Para POST /api/loading-orders:

* manter createdBy = req.user.id.
* não alterar payload.
* não alterar criação dos itens consolidados.

Para POST /api/loading-orders/:id/items:

* adicionar role gate Admin/Logística.
* adicionar ou preservar checagem de status para impedir item em ordem completed/cancelled.
* Se já existir helper de can-edit/status, reutilizar.
* Se não existir, fazer checagem mínima e clara.
* Não alterar payload.
* Não alterar regra de consolidação de itens além do bloqueio por status.

Para mark-ready/approve/disapprove:

* preservar as regras atuais de transição:

  * mark-ready exige draft.
  * approve exige ready.
  * disapprove exige approved.
* Apenas adicionar middleware de autorização.
* Não alterar nomes de status.
* Não alterar payload de resposta.

Para optimize:

* trocar check inline !req.user por middleware RBAC.
* Padronizar 401/403:

  * anônimo → 401 { error: "Não autenticado" }
  * sem papel → 403
* Não alterar algoritmo de otimização.
* Não alterar payload da otimização.
* Não alterar persistência dos resultados.
