Vamos refinar o modal de Novo/Editar Evento para ficar 10/10, sem scroll e mais fácil de preencher.

Arquivo foco:

* componente/modal de evento, provavelmente client/src/components/event-dialog.tsx ou equivalente
* client/src/pages/events.tsx, se necessário apenas para integração visual

Objetivo:
Melhorar o modal de criação/edição de evento para que ele fique compacto, sem scroll, com todos os campos importantes visíveis ao abrir e com preenchimento de datas/horas mais fácil para o usuário.

Problemas atuais:

* O modal ainda possui scroll vertical.
* O usuário precisa rolar para ver todos os campos.
* O campo Status não faz sentido no momento da criação.
* Os campos de data/hora são difíceis de preencher.
* O modal está visualmente bom, mas ainda pode ficar mais rápido e prático.

Regras principais:

* Remover o scroll do modal.
* Mostrar todos os campos principais na primeira visualização.
* Remover o campo Status do formulário de criação.
* Facilitar o preenchimento de datas e horários.
* Preservar payload, back-end, RBAC e regras existentes.
* Não criar novo Design System.

==================================================

1. MODAL SEM SCROLL
   ==================================================

Ajustar o layout para que o modal caiba inteiro na tela, sem rolagem vertical.

Direção visual:

* Modal mais largo no desktop, por exemplo max-w-4xl ou max-w-5xl.
* Layout em grid de 2 ou 3 colunas quando fizer sentido.
* Reduzir espaçamentos verticais excessivos.
* Reduzir altura de textarea.
* Evitar textos auxiliares muito longos.
* Footer sempre visível.
* Header sempre visível.
* Conteúdo completo visível sem scroll em desktop padrão.

Se em telas menores/mobile o scroll for inevitável, permitir apenas no mobile. No desktop, não deve haver scroll.

3. REMOVER STATUS DO MODAL
==========================

Remover o campo Status da criação do evento.

Na criação:

* o status deve ser definido automaticamente como “Planejamento”, se esse já for o padrão esperado.
* não exibir o campo para o usuário.

Na edição:

* se for necessário manter edição de status, avaliar uma destas opções:

Opção A:

* manter status oculto também na edição;
* status é alterado por fluxo próprio ou outra ação.

Opção B:

* mostrar status somente na edição, mas em uma área discreta chamada “Status do Evento”.
* não mostrar status no modal de Novo Evento.

Preferência:

* remover o status do modal de criação.
* manter o valor atual no payload sem quebrar o back-end.

Não alterar schema.
Não alterar status/transições.
Não alterar regra de negócio.

==================================================
4. FACILITAR PREENCHIMENTO DE DATA E HORA
=========================================

Trocar os campos atuais de datetime por uma experiência mais fácil.

Em vez de um único campo de data/hora difícil de preencher, usar:

* campo de Data
* campo de Hora

Exemplo:

Data de Montagem: [03/06/2026]
Hora: [16:20]

Data do Evento: [03/06/2026]
Hora: [18:00]

Data de Desmontagem: [04/06/2026]
Hora: [08:00]

Benefícios:

* usuário entende melhor;
* menos erro de digitação;
* layout fica mais compacto;
* mais fácil validar.

Ao salvar:

* combinar data + hora internamente para manter o payload atual.
* não alterar contrato da API se o backend espera datetime.

8. VALIDAÇÕES VISUAIS
=====================

* Nome do Evento
* Cliente
* Local
* Data de Montagem
* Hora de Montagem
* Data do Evento

* “A desmontagem não pode ocorrer antes do evento.”

Não alterar regras do back-end sem necessidade.
Apenas melhorar validação visual e manter backend seguro.
