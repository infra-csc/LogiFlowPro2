3. Regras de status / transição
Enum movementStatusEnum (shared/schema.ts:76)
created, pending_approval, in_progress, paused, completed, cancelled.

Transições válidas (definidas em R7, linhas 1742-1748)
created → in_progress | cancelled
in_progress → paused | completed | cancelled
paused → in_progress | cancelled
completed → ∅
cancelled → ∅
pending_approval não aparece na tabela — buraco lógico: aprovar/rejeitar muda status via storage sem passar pelas transições.
Regras de edição por status
Itens só podem ser adicionados/removidos/decrementados se status = in_progress (R8/R9/R10).
PATCH só permite ao criador editar quando status = created (linha 1730).
Aprovação só funciona se status = pending_approval (R13).
Rejeição idem (R14).
Onde pending_approval é setado?
Não está no fluxo de transição do R7. Provavelmente vem de storage.createMovementWithEvents quando movementTypeConfig.requiresApproval = true (campo em shared/schema.ts:442). Confirmar via auditoria do storage.ts antes de codar 2.8.
Aprovação obrigatória depende do tipo de movimento
movement_types_config.requires_approval (boolean) define se aquele tipo precisa de aprovação. Não há lookup desse flag nos middlewares — só na camada storage.
Audit trail
Existe movement_audit_logs (criados em R7, R8, R10, R12) com actor snapshot.
Existe audit_logs (global, criado em R13, R14).
R9 (decrement) não cria audit log. Pequeno gap.
