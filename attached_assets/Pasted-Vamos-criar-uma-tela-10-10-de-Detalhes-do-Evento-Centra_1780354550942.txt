Vamos criar uma tela 10/10 de Detalhes do Evento / Central do Evento.

Objetivo:
Quando o usuário clicar em um evento na tela de Eventos, ele deve abrir uma tela completa com tudo que está acontecendo naquele evento.

Essa tela deve funcionar como uma Central Operacional do Evento, mostrando requisições, itens, viagens, ordens de carregamento, movimentações, status, pendências e alertas.

Nome conceitual:
Event Control Center

Rotas/telas foco:
- client/src/pages/events.tsx
- criar ou refinar client/src/pages/event-details.tsx
- componentes relacionados a EventOverview/EventSummary, se necessário
- server/routes.ts, se for necessário criar endpoint agregado
- storage/repositories relacionados a eventos, requisições, loading orders, viagens, movimentações e estoque

Objetivo de UX:
O admin/logística/supervisor deve clicar em um evento e entender rapidamente:

- Qual é o evento?
- Qual cliente/local/data?
- Qual status?
- A janela de requisição está aberta, futura ou encerrada?
- Quantas requisições existem?
- Quantas estão pendentes, aprovadas ou rejeitadas?
- Quais itens foram solicitados?
- Quais itens foram aprovados?
- Quais ordens de carregamento existem?
- Quais viagens estão planejadas?
- Quais movimentações estão em andamento/finalizadas?
- Existem pendências ou riscos?
- O que precisa ser feito agora?

Usar o Design System atual do EventFlow como fonte única de verdade visual.

Não criar novo Design System.
Não alterar tokens globais sem necessidade.
Não inventar padrões paralelos.

PARTE 5 — ALERTAS DO EVENTO
==================================================

Criar seção “Alertas do Evento”.

Mostrar apenas quando houver alertas.

Alertas possíveis:

- requisições pendentes de aprovação;
- janela de requisição encerrando em breve;
- janela de requisição encerrada sem requisições aprovadas;
- evento próximo sem viagem planejada;
- evento próximo sem ordem de carregamento;
- ordem aprovada sem viagem;
- movimentação pausada;
- movimentação com itens excedidos;
- produto solicitado sem estoque suficiente;
- produto locado/terceiro sem fornecedor;
- ordem sem período definido;
- viagem sem motorista;
- viagem sem veículo;
- viagem sem destino.

Cada alerta deve mostrar:
- severidade;
- descrição clara;
- entidade relacionada;
- ação/link para resolver.

Exemplos:
- “2 requisições aguardam aprovação”
- “Evento ocorre em 5 dias e ainda não possui viagem planejada”
- “1 movimentação pausada precisa ser retomada”
- “3 produtos podem ter conflito de estoque”

Se não houver alertas:
- mostrar estado positivo discreto:
  “Nenhum alerta crítico para este evento.”

PARTE 8 — ITENS DO EVENTO
==================================================

Criar seção “Itens do Evento”.

Objetivo:
Mostrar uma visão consolidada dos materiais solicitados/aprovados para aquele evento.

Cada item deve mostrar:

- nome do produto/kit;
- SKU;
- quantidade solicitada;
- quantidade aprovada;
- quantidade carregada, se disponível;
- estoque disponível, se disponível;
- origem/área solicitante;
- status:
  - solicitado;
  - aprovado;
  - parcialmente aprovado;
  - carregado;
  - pendente;
  - conflito de estoque.

Se os dados estiverem disponíveis, consolidar por produto.

Exemplo:

Produto: Box Truss Q30
SKU: BOX_3Q30
Solicitado: 30
Aprovado: 25
Carregado: 12
Origem: Cenografia, Iluminação

Design:
- tabela compacta se houver muitos itens;
- cards compactos se houver poucos;
- SKU com font-mono text-xs;
- quantidades alinhadas;
- alertas discretos para conflito;
- sem cards gigantes.

Se consolidar itens exigir query complexa:
- criar endpoint agregado seguro;
- ou registrar como melhoria futura e mostrar itens por requisição inicialmente.

PARTE 13 — BACK-END / ENDPOINT AGREGADO
==================================================

Avaliar criar endpoint agregado:

GET /api/events/:id/overview

Esse endpoint deve retornar dados consolidados do evento:

- event;
- requisitionsSummary;
- requisitions;
- itemsSummary;
- loadingOrdersSummary;
- loadingOrders;
- tripsSummary;
- trips;
- movementsSummary;
- movements;
- alerts;
- timeline;
- recentActivity, se existir.

Importante:
- endpoint apenas leitura;
- requireAuth obrigatório;
- respeitar RBAC;
- não vazar dados que o usuário não poderia ver;
- limitar listas, exemplo top 5 ou top 10 por seção;
- permitir “Ver todas” levando para a tela específica filtrada por evento;
- evitar query pesada;
- usar joins/queries eficientes;
- não alterar contratos existentes.

Se criar endpoint agregado for arriscado:
- usar queries existentes no front;
- registrar endpoint agregado como melhoria futura.

Preferência:
Criar endpoint agregado, se for seguro, porque a tela precisa de muitos dados relacionados.

==================================================
PARTE 14 — RBAC
==================================================

Preservar RBAC atual.

Regras gerais:
- qualquer usuário logado que já pode ver eventos pode ver a central do evento conforme permissões atuais;
- ações de criar/editar só aparecem para quem pode;
- aprovações só aparecem/agem para Admin/Supervisor;
- logística só executa ações permitidas;
- usuário comum não deve ver ações administrativas indevidas.

Back-end continua fonte da verdade.

Não alterar:
- role_permissions;
- helpers de autorização;
- permissões globais;
- regras de negócio.
